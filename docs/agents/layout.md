# Layout

| Path | What it holds |
|---|---|
| `docs/` | Everything written down; see [docs/README.md](../README.md) |
| `scripts/` | Repo tooling: todo board check, doc-index check, worktree helpers |
| `.github/` | Workflows, dependabot, PR and issue templates |
| `.agents/skills/` | Skills; `.claude/skills` symlinks here |
| `Cargo.toml`, `Cargo.lock` | The workspace root and the `monitor-lizard` crate's own manifest ([ADR 0002](../decisions/0002-rust-core-polling-collectors-local-web-ui.md)); `[workspace] members = ["src-tauri"]` adds the shell below |
| `src/lib.rs` | Every module below as `pub`, so `src-tauri/` links against one copy of the code instead of recompiling it ([ADR 0004](../decisions/0004-tauri-menu-bar-shell.md)) |
| `src/main.rs` | CLI entry: `snapshot`, `json`, `serve`, `approve`, `privilege`, `watch`, `sudo-log`, `persistence`, `storage` |
| `src/collect.rs`, `src/group.rs`, `src/rules.rs`, `src/snapshot.rs`, `src/model.rs` | Process and socket collection, grouping by app, findings and the rule-based trust label (`rules::classify`), the snapshot type |
| `src/paths.rs` | Where state lives (`~/.monitor-lizard/`), with the one-time migration from whichever of `~/.sys-monitor/` or `~/.ownwatch/` is found, and the startup pass that makes the folder 0700 and its files 0600 |
| `src/baseline.rs` | The baseline of expected things (`baseline.json`: typed entries `app:`, `host:`, `startup:`, `finding:<app>:<rule>#<ports>`; at most 5,000 entries, written under a lock file; an old untyped file reads as apps; a corrupt one is kept as `baseline.json.bad`; `/api/baseline`, `POST /api/approve` and `/api/unapprove` take `kind` and `key`) |
| `src/history/` | The SQLite history (`history.db` under `src/paths.rs`'s data directory), one private module per table, each under 800 lines. The schema is versioned with `PRAGMA user_version`, see below. `mod.rs` holds the `History` type (one connection), `open`/`at`, `path()`, `open_or_report` and `unavailable`, and re-exports every public item, so callers keep writing `history::History` and `history::start_capacity_writer`. `migrations.rs` holds `MIGRATIONS`, `migrate`, the backup and the open lock. `seen.rs` holds first-seen hosts and the `notified` dedupe. `persistence.rs` holds startup items and the change list. `sudo.rs`, `actions.rs` and `baseline_changes.rs` hold the sudo launches, the action audit and the audit of every mark and unmark. `trash.rs` holds the Trash audit. `capacity.rs` holds `capacity_daily`: one row per local day for 90 days, made by `CREATE TABLE IF NOT EXISTS` when the database is opened rather than by a migration step; a writer thread keeps one connection, checks every 10 minutes, survives a panic in a check, logs failures, skips a sample while the newest row is dated slightly ahead of the clock and deletes rows dated more than a day ahead; it is independent of `metrics_history`; `GET /api/storage/history` reads it through a separate read-only connection that never creates or migrates anything. `metrics.rs` holds `samples`: downsampled CPU and memory at 1 and 15 minute resolutions, opt-in via `settings.metrics_history`, never per process. `test_util.rs` holds test helpers shared by more than one module. **To add a table,** create a file named for it with an `impl History` block, its row types and a `#[cfg(test)] mod tests`; declare it in `mod.rs` and re-export its public items there; then append a step to `MIGRATIONS`, or run a `CREATE TABLE IF NOT EXISTS` constant from `History::at` as `capacity_daily` does. Items another module needs are `pub(super)`. A test's full name includes its module, for example `history::migrations::tests::...` |
| `src/privilege.rs`, `src/watcher.rs` | Authorization-log parsing and the live sudo/su launch watcher. **Data:** each `Hop` of a captured chain stores pid, executable and command (cut at 300 characters) and, since P1, `started`, `tty`, `cwd`, `detail` and `more`. All are `#[serde(default)]`, so `sudo_events.chain` rows captured before P1 still load, with `detail: false`, and need no migration; `detail: false` is how the page tells "not recorded" from "not readable". `cwd` comes from `proc_pidinfo(PROC_PIDVNODEPATHINFO)`, which answers for the user's own processes only, and `more` marks a chain cut at `MAX_HOPS` (12). **Join:** `privilege::match_live` matches a failed authorization to the live row with the same pid and program, captured from 10 minutes before to 10 seconds after the log line; `privilege::recent(minutes, live)` sets each event's `source` (`captured`, `ps`, `none`) and `chain`, with one `ps` per refresh for the parents of the unmatched ones, cut at 300 characters. **Display:** `watcher::hop_label` names a hop with its script when the program is an interpreter, and `watcher::visible` (with the page's `visible`) turns control and format characters such as bidi overrides into visible `\u{..}` escapes wherever a command, folder or parent is shown or exported. `tests/fixtures/hop-labels.json` and `tests/fixtures/visible.json` are checked by both the Rust and the Node tests |
| `src/persistence.rs` | Read-only scan of launch agents, launch daemons and cron. Each item has a schedule, a fingerprint (SHA-256 via the `sha2` crate of the plist bytes and the program's signing identity; `codesign` results are cached per path and modified time in `collect.rs`), and, when gone, `removed_at`. A plist that cannot be parsed, is not a regular file or is over 8 MiB stays listed with `unreadable`. The plist is read once and the same bytes are hashed and given to `plutil` on stdin. A relative program path has no signing result and carries a `trust_note`. `take()` returns `{items, changes, truncated, scanned_at, scan_id}`, which `/api/persistence` serves; scans run one at a time behind a lock. `is_new` marks items first seen after the learning period, and also a marked item that has changed |
| `src/storage/mod.rs` | The scan: a fixed list of folders in a set order, allocated bytes, a 20 s budget with a quarter of the time left per location, coverage and category totals that say when they are a lower bound; `monitor-lizard storage` prints it. Read-only |
| `src/storage/rules.rs`, `src/storage/walk.rs` | `label_for` / `label_item`: one `safe`, `review` or `yours` label per path, `safe` only on an allowlist and never under user content; the `lstat` walker with entry cap, device check and pacing to about 20% of one core; the `node_modules` search and the idle test |
| `src/storage/trash.rs`, `src/trash_route.rs`, `src/query.rs` | `POST /api/trash`, contract in plan D15. `trash_route::parse` reads the query strictly (only `dry=0` moves, bad values are 400), policy checks `HOME` trust, ids from the latest scan (`Cache::find_in_generation`) and the single-use `ConfirmTokens` from a preview (bound to ids, labels, scan, `confirm_yours` and the previewed movable set; capped at 32), and I/O writes the audit and runs `trash::run`. `run()` checks each item (symlink, canonical form and case, home or `/Applications`, owner, yours confirmation, measured, mtime, length, entry count, no mount inside), calls `Audit::attempting` before the mover and repeats the path checks right before it; a mover failure, an audit failure or the 45 s budget stops the batch. The mover is `actions::trash` (`NSFileManager`) with a typed `MoveError`. `server.rs` runs the route on its own thread, one at a time. Audit: one `trash_items` row per item (`pending`, `moving`, then the result), about the newest 10,000 kept by whole request, unfinished rows marked `interrupted` at startup; the first table `trash_moves` is read-only legacy. `GET /api/history` returns them as `trash_moves` with `~` paths; `query.rs` holds `urldecode`, `random_token` and `secrets_equal` shared by the server and the route. Its two `hdiutil` mount tests skip when `GITHUB_ACTIONS` or `CI` is set (the mount refusal is verified locally only); `ML_RUN_MOUNT_TESTS=1` runs them, see [commands](commands.md) |
| `src/requester_signal.rs` | `POST /api/requester/signal` and `GET /api/requester/status`: freeze (STOP), resume (CONT), stop (TERM) or force stop (KILL) the hops of a sudo requester chain, one process or the whole chain. Contract in the module comment: `action`, `scope` (`one`/`chain`), one `item=<pid>:<started>:<exe>` per process child first (at most 12), preview unless `dry=0`, single-use `confirm_token` (reuses `trash_route::ConfirmTokens`, its own instance). `World` is the trait over `ps`, libproc and `kill(2)` that tests fake; `verify` is the one place a pid is accepted: not pid 1, not Monitor Lizard or its parents and descendants (`related_to`), still running, start time and executable equal to the captured hop (else `pid_reused`), not root (`root_owned`) or another user (`not_yours`), and the action fits the state (`already_frozen`, `not_frozen`; one `proc_pidinfo` call gives uid, state, parent and start time), CONT only goes to what the audit log shows this app froze (`not_frozen_by_us`), `scope=chain` items must be parent and child (`not_a_chain`), and a hop that looks like the owner's own session (`danger_reason`: program names of the executable and argv0, app bundles and `claude` words on any path, an unreadable command for an interpreter; lists and cases mirrored in `tests/fixtures/danger-hops.json` and in `page-signal.js`) needs an explicit `confirm_danger=1` on preview and commit (`needs_danger_confirmation`; a deliberate second step, not an authorisation boundary); the ancestor/descendant table is fail-closed (`unverifiable`). Every pid is checked at preview, before the audit row and again just before its own signal. One audit row per signal to be sent (`record_action`, STOP/CONT/TERM/KILL) is written first and nothing is signalled if it fails; a planned signal that is not sent gets an `unsent <SIGNAL>` row and `froze_by_log` skips the planned row it cancels; Stop on a frozen process plans TERM then CONT; if the TERM already ended the process, the result lists only `TERM` and the CONT is an `unsent CONT` row, counted as success only when the process is verifiably gone; one request at a time (`busy`); `GET /api/requester/status` needs the token (checked before any `ps`), lists children only for fully verified processes, and reports `chain_code` per item; a second row records anything refused or failed later. Freeze and resume go parent first, stop and force stop child first; Stop on a frozen process also sends CONT. Tests signal only `sleep` processes they start (detached, so they are outside Monitor Lizard's own tree) |
| `src/storage/forecast.rs` | Capacity history: the `Day` sample (used, purgeable, free bytes, nothing about apps or folders), `forecast()` (least-squares line over the last 14 days of used including purgeable; needs 7 samples; fits only the days after a one-day fall of more than 5% of the disk; range from the slope's standard error), `week_change()` and `reply()` (which also says how old the last sample is and `stale` after 2 days), the body of `GET /api/storage/history` (read-only, no token; a database that cannot be opened gives `available: false`, still a 200) |
| `src/storage/volume.rs`, `src/storage/cache.rs` | Capacity split into used, purgeable and free (CoreFoundation, no root) and local snapshots from `tmutil`; the cached result served at `/api/storage`; the Storage page's Growth block reads `/api/storage/history` (`?fresh=1` starts a scan at most once a minute). `/api/volume` serves the capacity alone, read on each request with no scan, for the Disk and network tab |
| `src/netif.rs` | Counts network interfaces that are up, running and hold a routable address (`getifaddrs`; loopback and link-local-only interfaces are left out). The sampler stores it as `network.interfaces_up`, so the page can tell no connection from an idle one |
| `src/actions.rs`, `src/server.rs` | Guarded Stop/Quit and the loopback HTTP server. `check(pid, uid, expected_start)` re-reads the pid's start time fresh (`procusage::live_start_unix`) and refuses on any mismatch, so a recycled pid is never signalled; `is_signalable(pid, uid)` (used by `classify::allowed_actions`) shares `check`'s own ownership check but has no particular instance's start time to defend, for a plain "can this pid ever be signalled" query. `POST /api/kill` requires `start=` to pair 1:1 with `pids=` |
| `src/web.rs` | The dashboard files, each an `include_str!` in `SOURCES` (`/`, `/app.css`, `/js/<file>.js`; a path not listed is a 404 and nothing is read from disk), the per-run token put into the shell, and `reply`, the one function the server and the tests share for these paths: the Host check (403), a refusal of `Sec-Fetch-Site: cross-site` or `same-site` for the stylesheet and scripts (403; an absent header, `same-origin` and `none` pass), and the headers `content-type`, `cache-control: no-store` (the page holds a per-run secret, so a stale shell with a cached script after a restart must not happen) and `x-content-type-options: nosniff` |
| `src/sampler.rs` | 2 s background sampler (CPU, memory, network, load, GPU, disk), 1-hour ring buffer, served at `/api/metrics?since=` |
| `src/iokit.rs` | Cached IOKit service handles for GPU utilization (`IOAccelerator`) and disk throughput/capacity (`IOBlockStorageDriver`, `statfs`), no process spawning |
| `src/procusage.rs` | Per-process CPU, memory and disk I/O via `proc_pid_rusage` every 5 s, keyed by (pid, start time); `ps`-derived fallback for another user's processes; `/api/processes?sort=&limit=` or `?pids=` for specific rows. Every row carries `start_unix` (`kern.boottime` plus the converted mach-abstime start, unavailable for another user's process); `live_start_unix(pid)` is a separate, always-fresh single-pid read `actions::check` uses for the recycled-pid defense, never the 5 s cache |
| `src/classify.rs` | `Action`, `allowed_actions(label, group)`, and the bounded `Evidence` record for one group -- what the classifier agent (A8) is allowed to suggest and see; `validate_verdict(rule_label, allowed, verdict) -> Verdict` clamps A8's raw reply to never escalate below the rule label and never suggest an action outside `allowed` |
| `src/settings.rs` | `~/.monitor-lizard/settings.json`: notification level, quiet hours, generic text, seeded |
| `src/notify.rs` | Deduplicated macOS notifications for high findings via `osascript`, off by default |
| `src/llm.rs` | One blocking call to a local llama-server with a JSON-schema response format, parsed into a `Verdict`; clamping against the rules is A10 |
| `src/model_store.rs` | Downloads and verifies the local classifier model: `MANIFEST` pins the repo, commit, file name, size, SHA-256 and licence for each `--model` choice, in the binary, not fetched from the Hub at install time. `install` resumes a partial download by `Range`, restarts cleanly if the server ignores it, and deletes the temp file on a hash mismatch; `status` reads and hashes the local file only, no network. `monitor-lizard model install [--model qwen3-4b\|qwen3-1.7b] [--yes]` / `model status` |
| `src/llm_server.rs` | Supervises a local `llama-server` child process behind `settings.agent_enabled` (the kill switch, `monitor-lizard agent on\|off`): spawned loopback-only with a cleared, allowlisted environment (`PATH`, `HOME`, `TMPDIR`, `LANG`) once the model is installed (`model_store::status`), memory pressure is not critical (`sampler::pressure_level`) and `llama-server` is found (Homebrew's usual paths, then `PATH`); health-checked at `/health`, restarted with capped exponential backoff on a crash. `LlmServer::base_url_if_ready`/`reason` are its whole read surface; `POST /api/classify?group_key=` (`src/server.rs`) is the only caller, falling back to the rule label alone (`classify::validate_verdict`) whenever the agent is not ready |
| `web/index.html`, `web/app.css` | The dashboard shell and stylesheet. The shell is markup, the theme bootstrap, `<meta name="ml-token" content="__TOKEN__">` and one `<link>` and `<script src>` per file. **The meta tag must keep the exact `__TOKEN__` text**: the server replaces it in the shell only and `core.js` reads it. No script may hold the token, because a script is a fixed URL that any website can load and read; the shell's body cannot be read across origins. The split changed no behaviour except this token location, the 403 for cross-site loads of the stylesheet and scripts, and `cache-control: no-store` on every web file (the single page sent none). The Moss palette lives once, as custom properties in two blocks at the top of `app.css` (dark, then `:root[data-theme=light]`). Every other rule and script uses `var(--token)`, never a hex. Green (`--acc`) means brand and selection, cyan (`--ok`) means healthy, and `--s2` is the second chart series. `tests/web/theme-contrast.test.mjs` holds the contrast ratios, so check it after changing a token |
| `web/*.js` | Classic scripts that share globals (no modules, no build step), loaded in a fixed order, listed in the shell and in `SOURCES` in `src/web.rs`. No file is over 800 lines. Hoisting stops at a file, and a top-level throw in one script no longer stops the next, so code that runs while loading belongs in the file after what it uses |
| What each script holds | `core.js` (the token read, shared state `S`, the `h` builder, the `disk-net`, `memory-tab`, `actions`, `view-items`, `url-state`, `guide-search` and `guide-copy` blocks, `rec`/`quiet`, theme, dropdown, paging; it mixes small pure blocks because a block stays next to the code it was moved with), `table.js` (sorting, the `requester`, `export`, `export-cols`, `floor` and `colresize` blocks, table decoration, the shared `beginDrag` drag-listener helper used by column and drawer resize), `data.js` (`api`, pollers, stop and approve), ten `page-*.js` (overview, apps, privilege, listeners, persistence, network, history, performance, storage, guide), `chart-hover.js` (loads before `page-performance.js`: the pure `chart-hover` block and the `chart-hover-view` block, whose `chartHost` wraps a chart's svg with a guide line, a dot per series and a tooltip, and keeps the highlight in `CH` so a poll redraw restores it), `helpers.js` (the `page-shell` block), `page-storage-logic.js` (the `storage-page`, `storage-cleanups` and `storage-trash` blocks), `search.js` (the global search: the pure `global-search` block, then the `global-search-view` block, whose box, menu and key handling the shell starts with `searchInit()`; it loads after `page-guide.js` because it reuses the Guide's search and `announce`). `page-storage.js` also holds the `storage-trash-view` block. `shell.js` holds the page shell, sidebar, `render`, event wiring and startup, and it runs last. Below 860px (the breakpoint also in `web/app.css`) the sidebar collapses behind a hamburger toggle (`#navtoggle` in `web/index.html`) into a fixed off-canvas drawer (`.side` under `@media(max-width:860px)`); `openNav`/`closeNav` in `shell.js` toggle `S.navOpen`, a backdrop (`.navbackdrop`, reusing `.overlay`'s look) closes it on click, a nav item's own click closes it and moves focus to `#main`, and a `resize` listener closes it if the window widens past the breakpoint while it is open. `closeTopLayer` (`page-storage.js`) treats the open drawer as the lowest-priority layer Escape closes. |
| Adding a dashboard page | Add `web/page-<name>.js` with its renderer and loaders, its `<script src="/js/page-<name>.js">` tag before `helpers.js`, the same line in `SOURCES` in `src/web.rs` and the view in `NAV` and `render()`. `cargo test` fails when the tags, `SOURCES` and the files on disk disagree |
| How tests find web code | `tests/web/page.mjs` puts the stylesheet and scripts back into the shell in tag order; a test lifts a marked block by name, and each marker pair appears once, in the file that holds its code. |
| `tests/web/` | Node logic tests for the dashboard (`node --test`). `tests/web/page.mjs` puts the stylesheet and the scripts back into the shell in load order, so a test lifts a block or reads markup without knowing which file holds it; a marked block stays with its code. `tests/web/split.test.mjs` checks the load order (every script runs in a stand-in browser, and a wrong order fails) and where the token lives. They extract the marked `url-state`, `export`, `requester`, `guide-search`, `guide-copy`, `global-search`, `global-search-view`, `page-shell`, `view-items`, `disk-net`, `memory-tab`, `actions`, `floor`, `colresize` and `storage-page`, `storage-cleanups`, `storage-trash`, `storage-trash-view`, `signal`, `signal-view`, `chart-hover`, `overview-page`, `network-page` and `persistence-page` blocks from the dashboard scripts. The `colresize` block (`tests/web/table-colresize.test.mjs`, alongside `tests/web/table-floor.test.mjs`'s `floor` block) holds the pure math behind a dragged or arrow-keyed table column: `isFlexTrack` (only a flexible `fr` track is resizable), `applyColumnWidths` (overrides a flexible track with a stored px width, clamped to its own minimum) and `clampDrag` (the shared delta-clamp math a drag and an arrow-key step both call). `widthsOf`/`setWidth` persist the chosen widths per table and column id under their own `table-colw:` localStorage key, parallel to `hiddenOf`/`setHidden`'s `table-cols:` key for the column chooser; a stale width (a since-renamed or removed column id) is simply ignored. The column grip and the drawer handle share one `beginDrag` listener-wiring helper (only one drag is ever in progress at a time). The `disk-net` block holds capacity bar sizing, rate formatting and the no-connection state. The `memory-tab` block holds the memory pressure level's colored tag and the "no swap" state. The `actions` block holds the Stop/Quit confirm dialog's logic: which pids a fresh `/api/processes?pids=` read actually confirms (`confirmable`, always already-unwrapped plain values, never a `Reading<T>`) and the fresh-evidence sentence (`evidenceLine`). The `storage-page` block holds the Storage page's scan state, "at least" wording, treemap tiles and columns, and table rows, and the capacity history wording and chart geometry; it reads `url-state`, `disk-net` and `page-shell`. The `storage-cleanups` block holds the clean-ups ranking, the Inside System Data rows, the picked-folder sums and the exported report builder (`reportHtml`, which escapes every name and loads nothing remote). The `storage-trash` block is the Move to Trash flow as a pure state machine (`trashStep(state, event)` returns the next state and the effects to run; phases idle, previewing, previewed, confirming-yours, moving, done, error), with `trashSelection` (what the picked rows allow), `trashSummary` (a reply read defensively, counting only `moved` as moved, with a warning when the server's own totals disagree), `trashHistoryRows` (the History page's Moves to the Trash rows), `trashProblem` (one plain message per server refusal) and `trashUrl`. The dialog around it is in the `storage-trash-view` block of `page-storage.js` (`trashLayer`, `trashDialog`, `trashSync`, `closeTopLayer`); every name and server text goes through `visible()`: it sends ids, never paths, through `api()`, which throws an error with `status` and `text` so the flow can read a 409, 429 or 500 body. `tests/web/storage-trash.test.mjs` covers the logic and `tests/web/storage-trash-view.test.mjs` the dialog against a stand-in DOM. The `signal` block (`web/page-signal.js`) is the freeze/resume/stop dialog as a pure state machine (`sigStep(state, event)`; phases idle, previewing, previewed, confirming-danger, sending, done, error), the severity classifier `sigSeverity` (danger: the lists mirrored from Rust; caution: an interpreter, a process with children, or one whose children are not known yet; plain), `sigAvail` (which buttons a hop's live state allows) and `sigSummary`; the `signal-view` block draws the buttons under each hop of an open requester detail (`sigControls`) and the dialog (`sigDialog`, `sigLayer`), polls `GET /api/requester/status` for the open details (`loadReqLive`), escapes every command line and path with `visible()`, and sends hop evidence (pid, start time, executable) in the POST query, never the address hash. `tests/web/signal.test.mjs` covers the logic and `tests/web/signal-view.test.mjs` the buttons and dialog against a stand-in DOM. The `chart-hover` block holds the chart reading. Its functions: `chartIndexAt` (a pointer fraction snaps to the nearer sample). `chartStep` does arrow, Home and End stepping. `chartIndexForTs` (a keyboard highlight kept as a time survives the poll redraw, and among samples sharing a time the one nearest the last highlight wins), `chartTipLeft` (keeps the tooltip inside the chart), `chartAgo` ("32s ago") and `chartSample` (the rows a tooltip shows, with the reason for an unavailable value); `tests/web/chart-hover.test.mjs` covers it. `tests/web/chart-hover-view.test.mjs` runs the `chart-hover-view` block and the `perf-window` block (`downsample`, `perfWindowed`) against a stand-in DOM: the highlight across redraws, focus, blur, Escape, touch, and `chartFrame` pruning. `tests/web/perf-reading.test.mjs` covers the `perf-reading` block (`rv`, `rReason`) and the `preventScroll` focus restores. Chart tooltips sit over the chart and never inside a dimmed element. The `overview-page` block (`page-overview.js`) holds three pure functions. `lookedSince` sets the last-visit window: a first visit or a bad stored time covers 24 hours, and an old one is cut to 30 days. `feedRows` builds the "Since you last looked" feed, and `machineRows` builds the Machine strip. The page stamps the visit in `localStorage` when it is hidden or closed, so the feed does not change while it is open. `tests/web/overview-page.test.mjs` covers it. The `network-page` block (`page-network.js`) holds the Network page's filter test and counts (`netMatches`, `netCounts`), Group by (`netGroup` merges app rows by host or by port and keeps the app-row fields, so a merged row sorts and exports like an app row), the default order, the inspector facts (`netFacts`), the first-seen wording for a host older than the history (`netFirstSeenText`) and the copy text for an address (`netCopyAddress`, which brackets IPv6). `tests/web/network-page.test.mjs` covers it. The `persistence-page` block (`page-persistence.js`) holds the Persistence page's pure logic. It covers the filter test and counts, the Apple toggle, the change list (`persChangeRows`), the reasons an item is flagged (`persWhy`) and the signing text. A search always reaches Apple items, and `persWhy` reads only the item's own fields. `tests/web/persistence-page.test.mjs` covers it. The `requester` block holds the hop label, the app summary, the per-hop facts and the chain text and JSON used by the Privilege page and its export. Keep `url-state`, `export`, `requester`, `page-shell`, `storage-page`, `storage-cleanups`, `memory-tab`, `actions`, `guide-search` and `global-search` free of DOM and storage access. `global-search-view` (in `web/search.js`, the box, menu and keys) is the part that touches the DOM, and `tests/web/global-search-view.test.mjs` runs it against a stand-in DOM. The folder `tests/fixtures/` holds the Guide table and the search results that `cargo test` and the web tests both check |

## Change the database schema with a migration

`MIGRATIONS` in `src/history/migrations.rs` is an ordered list of SQL steps, and `PRAGMA user_version` is how many have run. To add a column or table, append one step at the end; never edit or reorder a step that has shipped, because installed databases already ran the old text.

- Each step runs in its own transaction. A failing step rolls back and `open()` returns the error.
- The first time an unversioned database is migrated, `history.db.bak` is written next to it (once; never overwritten).
- Step 1 relies on `IF NOT EXISTS`, so an old database with a table that lacks a column is not repaired. Fix that with a later step, not by editing step 1.
- Opening takes an exclusive lock on `history.db.lock`, so one process at a time reads the version, makes the backup and migrates.
- A database whose version is higher than the list is refused untouched. Downgrades are not supported.
- A new table that nothing alters later can still be a `CREATE TABLE IF NOT EXISTS` inside a new step.
- Test a step on a database built at the previous version, as the `a_step_added_later_...` test does.
- Step 3 adds `fingerprint`, `removed_at`, `schedule`, `changed_at` and `restored_at` to `persistence` with `ALTER TABLE ADD COLUMN`. A row from before it has a NULL fingerprint, which the next scan fills in without reporting a change. A scan writes a row only when an item is new, changed, removed or restored.
- Startup items: `changes` covers the last 30 days and at most 200 entries, newest first, and `truncated` says when entries were left out. A removed row is deleted 90 days after `removed_at`. The baseline date is the first scan plus the learning period.
- A startup mark is `startup:<plist path>#<fingerprint>`, made by the server from the item's `mark_key`. An item is expected only while its fingerprint equals the marked one. A bare `startup:<path>` entry (legacy, hand-written) matches any version.
